# M0_Templant_FreeRTOS 工程总结

## 1. 工程概述

这是一个基于 **TI MSPM0G3507** 的 **FreeRTOS 模板工程**，使用 **Keil uVision** + **SysConfig** + **DriverLib** 开发。

### 当前功能
- LED 心跳灯
- UART0 串口收发
- OLED(SSD1306) 显示测试
- FreeRTOS 多任务运行

### 主要引脚
- **OLED I2C0**
  - PA28 = SDA
  - PA31 = SCL
- **LED**
  - PB22
- **UART0**
  - PA10 = TX
  - PA11 = RX

---

## 2. 工程结构

- `main.c`：系统初始化 + 创建任务
- `Component/led/`：LED 驱动
- `Component/UART/`：UART0 驱动
- `Component/oled/`：OLED 驱动（硬件 I2C）
- `ti_msp_dl_config.*`：SysConfig 生成的外设配置
- `FreeRTOSConfig.h`：FreeRTOS 配置
- `keil/`：Keil 工程文件和启动文件

## 4. 遇到的问题与解决方案

### 问题 1：OLED 刷新卡死

#### 现象
- OLED 初始化前半段正常
- 在 `OLED_Clear()` / `OLED_Refresh()` 的第一条命令处卡住
- 一开始表现为 I2C 发送过程一直等待 `DL_I2C_getControllerStatus()`

#### 原因
- I2C 传输时序和等待逻辑与参考工程不一致
- 超时机制依赖 FreeRTOS tick，但此时调度器还没启动，导致超时无效
- I2C 总线异常时没有足够的恢复手段

#### 解决方案
- 按参考工程思路调整 I2C 发送逻辑
- 加入总线恢复函数 `oled_i2c_sda_unlock()`
- `OLED_Init()` 开头先检测 SDA 状态，必要时释放总线
- OLED 显示逻辑保留 GRAM 缓存，刷新时统一输出

---

### 问题 2：进入 FreeRTOS 后 HardFault

#### 现象
- 串口第一条信息可以打印
- 4 个任务无法正常运行
- Debug 停在 `HardFault_Handler` 的死循环里

#### 诊断结果
- 通过 HardFault 诊断信息定位到：
  - `PC = 0x00000B6E`
  - 对应标准库内部 `_memset_w`
- 结合任务和库调用分析，根因是 **主栈 MSP 太小**

#### 原始配置
- `Stack_Size EQU 0x00000800`（2KB）

#### 原因分析
- MSPM0 上 FreeRTOS 的 SVC / PendSV / SysTick / UART ISR 都会使用 **MSP**
- 工程里还使用了 `snprintf()`，标准库栈开销较大
- 2KB 的主栈不够，导致栈溢出、内存破坏，最终 HardFault

#### 解决方案
- 将启动文件里的栈改大：
  - `Stack_Size EQU 0x00001000`
- 即 **4KB 主栈**
- 修改后，FreeRTOS 任务正常运行

## 6. 经验总结

1. **MSPM0 的 FreeRTOS 工程里，MSP 主栈不要配太小**
   - ISR、SVC、PendSV、标准库都会吃栈
   - 2KB 很容易不够

2. **I2C OLED 最好按参考工程的时序写**
   - 先处理总线状态
   - 再发控制字节和数据
   - 加总线恢复机制

3. **`snprintf()` / `printf()` 在嵌入式里要注意栈开销**
   - 尤其在 FreeRTOS 中多个任务同时用标准库时

4. **先确认基础系统能跑，再加外设功能**
   - 先保证调度器和任务稳定
   - 再叠加 OLED / UART / 其他模块
