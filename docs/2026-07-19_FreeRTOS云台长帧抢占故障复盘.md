# 2026-07-19 FreeRTOS 云台长帧抢占故障复盘

## 写给后续模型的结论

遇到“步进电机能使能、有保持力、能查询位置，但 13 字节位置命令不转”的现象时，不要先怀疑 PD 参数、轴映射或电机协议。必须先计算一帧在 UART 线上的持续时间，并检查发送任务是否会在帧中间被更高优先级任务抢占。

本项目的最终根因是：115200 baud 下，Emma/X42S 的 13 字节 `FD` 位置帧需要约 1.13 ms；步进服务任务优先级为 2，视觉任务优先级为 3 且每 1 ms 唤醒。视觉任务即使“不再输出控制命令”，仍会运行并抢占步进任务，造成 `FD` 帧中间出现驱动器不能接受的字节间隔。3 字节位置查询和 6 字节使能帧可在一个 tick 内完成，因此一直正常，制造了“UART 没问题”的假象。

最终修复是在发送完整电机帧期间调用 `vTaskSuspendAll()`，发送完成后调用 `xTaskResumeAll()`。这只暂停任务调度约 1.2 ms，不关闭 UART 中断。修复后 pitch 的 400 脉冲命令立即得到 `FD/02` 接收响应并产生明显转动，反向 400 脉冲也成功回到原位附近。

## 已验证事实

- MCU 实际组出的 400 脉冲帧为：

  `01 FD 00 00 3C 14 00 00 01 90 00 00 6B`

- 帧含义：地址 1、CW、60 RPM、加速度 20、400 脉冲、相对模式、立即执行。
- 修复前：pitch 请求 400 脉冲，位置 `-2493 -> -2493`，没有 `FD` 响应，肉眼无运动。
- 修复后：pitch 请求 400 脉冲，位置 `-2493 -> 5719`，收到 `FD/02`，肉眼观察到明显转动。
- 反向回退：pitch 请求 -400 脉冲，位置 `5699 -> -2501`，再次收到 `FD/02`，机械位置回到测试前附近。
- Emma 位置查询值不是“角度”，而是约 65536 编码器计数/圈。当前电机命令细分为 3200 脉冲/圈，因此 400 脉冲理论对应 8192 编码器计数，实测约 8200，吻合。
- yaw/pitch 都曾出现“大命令不转”，所以不是单轴机械故障或单路 UART 故障。

## 为什么 FreeRTOS 下会失败

UART 115200、8N1 时，每个字节在线上需要 10 bit：

`13 × 10 / 115200 ≈ 1.128 ms`

本工程当时的调度关系：

- `VISION`：优先级 3，周期 1 ms；
- `GIMBAL_AT`：优先级 3；
- `STEPPER`：优先级 2，实际执行 UART 发送；
- FreeRTOS tick：1 ms。

调参任务只是把运动命令放入队列，真正写 UART 的是低优先级 `STEPPER` 任务。它发送 13 字节时必然跨过一次 tick；高优先级视觉任务就绪后会抢占。互斥锁只能阻止另一个任务同时访问 UART，不能阻止持锁任务被调度器抢占，所以“已有 TX mutex”并不代表帧在时间上连续。

正确处理：

```c
lock_tx(axis);
vTaskSuspendAll();
for (index = 0; index < length; index++) {
    DL_UART_transmitDataBlocking(instance, data[index]);
}
(void)xTaskResumeAll();
unlock_tx(axis);
```

不要用 `taskENTER_CRITICAL()` 包住整个 1.2 ms 帧。临界区会关闭中断，可能丢失 UART RX、系统 tick 或其他实时中断；暂停任务调度已经足够，同时允许 UART RX ISR 继续运行。

## “暂停视觉”必须包含三层

后续模型不得只设置一个 `control_enabled=false` 就声称视觉已经暂停。完整接管顺序应为：

1. 禁止视觉任务继续提交新电机命令；
2. 等待至少一个视觉命令周期，使已越过判断点的那次迭代结束；
3. 清空 MCU 中尚未执行的视觉运动队列；
4. 向两轴发送 `FE 98` 立即停止，终止驱动器内部正在执行的旧视觉运动；
5. 等待停止命令出队和机械稳定；
6. 确认两轴保持使能，再提交开环扰动；
7. 扰动和位置核验完成前不得重新开启视觉；
8. 失败导致丢靶时，先用等量反向开环命令退回，再恢复视觉。

“视觉不再计算输出”和“电机已经停止响应此前视觉命令”是两件不同的事。

## 本次犯过的错误

### 1. 没有先算 UART 帧时长

如果一开始计算 13 字节需要 1.13 ms，并对照 1 ms tick 和任务优先级，就能立即把检查重点放在帧原子性，而不是连续修改模式、轴映射和扰动幅度。

### 2. 被短帧成功误导

`F3/02` 使能响应和 `0x36` 位置查询都正常，只能证明 UART 引脚、地址和波特率基本正确，不能证明 13 字节长帧连续。必须按“短帧、长帧”分别验证。

### 3. 把“已写入 UART”当作“已经运动”

旧调参器只检查 `last_tx_ok` 和发送计数。它们只能说明 MCU 调用了发送函数。今后至少要同时检查：

- `FD/02` 驱动器接收响应；
- 扰动前后编码器位置差；
- 图像误差是否按预期离开死区；
- 肉眼运动只作为辅助证据，不能替代数据。

### 4. 把一次扰动拆成连续 20 脉冲

连续小段命令会改写未完成的实时目标，不能保证累计得到请求位移。调参扰动应提交一条有界命令，再等待和验收实际位移。

### 5. 烧录后只 Resume，没有 Reset

Keil 下载后目标处于 Halt。直接 Resume 可能从烧录前的旧 PC 继续执行，而不是从新固件复位向量启动。正确流程是：

1. `reset_and_halt()`；
2. 检查 PC 位于复位入口；
3. `resume()`；
4. 等待 RTOS 和外设初始化完成；
5. 再做邮箱预检。

后续自动调参脚本必须默认执行这个流程。

### 6. 过早相信旧日志中的轴标签

`tracking_vision` 的最终实机日志记录过 Yaw=UART1/PB6-PB7、Pitch=UART2/PA23-PA24；当前 FreeRTOS 工程和另一个集成工程标注相反。早期日志中又有“尚未实机验证”的配置。后续判断轴映射时必须按证据等级排序：

1. 当前实物单轴运动观察；
2. 当前固件的编码器和 `FD` 响应；
3. 明确写有“实机验证”的日志；
4. 源码注释、分支名称和未验证日志只能作为线索。

本次最终根因与轴映射无关，两轴都受相同长帧抢占影响。

### 7. 在没读代码前错误归因调试器轮询

曾怀疑电脑端每 50 ms Halt MCU，但复核后发现 `read_header()` 使用运行中 SWD 内存读取，并不会 Halt；只有最终完整快照才暂停。以后提出时序结论前，必须先逐行确认实际调用链，不能用“调试器通常会……”代替证据。

### 8. 错认位置反馈单位

曾把位置差直接解释为角度。实际数据证明它是编码器计数。任何物理量都必须通过已知整圈计数或一次可控运动标定，不能凭字段名字猜单位。

## 后续模型必须执行的排障顺序

当出现“保持力正常但运动命令不转”时，严格按以下顺序，不得跳步：

1. 确认烧录后做过 Reset，并读取当前 PC/启动状态。
2. 确认目标持续运行，没有被调试器留在 Halt。
3. 用短帧验证 UART：使能响应、位置查询响应。
4. 计算最长控制帧在线时长，与 RTOS tick、任务优先级比较。
5. 检查 UART mutex 之外是否还有调度抢占；长帧发送必须具备时间原子性。
6. 在 RAM 中记录实际长帧，逐字节核对地址、命令、方向、速度、加速度、脉冲、模式、同步位和帧尾。
7. 只做一个轴、一个方向、一次命令；视觉软件输出和驱动器内部旧运动都必须停止。
8. 同时记录发送结果、驱动响应、位置前后值和图像误差。
9. 单轴链路通过后再运行 PD 搜索；不得用调 Kp/Kd 掩盖底层执行器故障。
10. 失败时自动回退机械位置、恢复保持力、恢复视觉，并保存全部原始证据。

## 自动调参前的强制验收门槛

在运行任何 Kp/Kd 网格搜索前，必须通过以下测试：

- yaw 单次 120 脉冲：收到 `FD/02`，编码器位移达到理论值的至少 50%，图像横向误差离开 ±4 px 死区；
- pitch 单次 120 脉冲：同样通过；
- 正反向命令可以回到起点附近；
- 扰动阶段视觉命令计数不增加；
- 丢靶或异常退出能自动反向退回；
- 调试器断开后 MCU 保持 Running；
- 任何一项失败都不得开始参数搜索。

## 最终原则

实时系统里的串口协议不仅是“字节内容正确”，还包括“字节之间的时间连续”。在裸机代码迁移到 FreeRTOS 时，凡是帧持续时间接近或超过一个 tick，都必须主动审查任务抢占、DMA/FIFO、调度锁和驱动器帧超时。短帧能工作绝不等于长帧能工作，保持力存在也绝不等于位置控制链路正常。
